TRAFKINTU (MVP escalable, arquitectura + patrones)

Construye una app web llamada TRAFKINTU (marketplace de emprendimientos/pymes en Chile) usando Next.js 14+ App Router, TypeScript, TailwindCSS y shadcn/ui. El objetivo es entregar un MVP frontend escalable con arquitectura limpia, patrones correctos y componentes reutilizables, usando datos mock por ahora, pero dejando todo preparado para conectar Supabase más adelante sin retrabajo.

0) Principios obligatorios (no negociables)

Separación de responsabilidades: UI / domain / data

Arquitectura por features (vertical slices), no por tipo (no un /components gigante sin orden)

Patrón Repository + Service para acceso a datos (mock hoy, Supabase mañana)

Patrón Container/Presentational: páginas/containers orquestan, componentes presentacionales son puros

DTOs y tipos: entidades del dominio tipadas, sin any

Escalabilidad: rutas, componentes, hooks y layout preparados para crecer (pagos, SII, reviews, geolocalización después)

Accesibilidad básica: labels, focus states, botones, links correctos

1) Stack y librerías

Next.js App Router /app

TypeScript

TailwindCSS

shadcn/ui (Button, Card, Input, Badge, Tabs, Dialog, DropdownMenu, Select, Textarea, Avatar, Separator, Skeleton, Toast/Sonner)

lucide-react

NO backend real por ahora: usar mocks e in-memory store (o simple state) detrás de repositorios.

3) Patrones de diseño obligatorios (aplícalos en el código)
3.1 Repository Pattern

Definir interfaces en domain/ports:

AuthRepository

MarketplaceRepository

PymeRepository

AdminRepository

Implementación mock en data/repositories/*MockRepository.ts usando seed data en data/mock/seed.ts.

3.2 Service Layer

Crear servicios puros:

domain/services/rankingService.ts (destacados primero, luego fecha)

domain/services/searchService.ts (filtrado por title/desc/cat/pyme)

features/*/services/*Service.ts (casos de uso: createListing, toggleActive, requestFeatured)

3.3 Container/Presentational

Pages como containers: obtienen data vía hooks/services y pasan props

Componentes como ListingCard, PymeHeader, ListingGallery sin lógica de fetch

3.4 State Management (simple pero escalable)

Usar un Provider liviano por módulo (Context + reducer) o un store simple (sin librerías extra) para:

session/auth mock

marketplace listings

featured requests

Debe estar encapsulado dentro de features (no global sin orden).
